# 数据后续阶段门槛与连接器边界

> 决策日期：2026-08-19  
> 状态：已采纳  
> 范围：ERP 数据模块、TikTok Shop Analytics，以及可能的 TikTok Business/创作者数据连接器

## 1. 决策摘要

1. 当前阶段只做 TikTok Shop Analytics 日级数据的稳定性、完整性和多店铺灰度验收。
2. 小时级实时数据、更多视频字段、直播商品明细、广告归因和导出功能，在稳定性门槛通过前不得进入实现阶段。
3. 如果 TikTok Shop 官方接口或当前 Seller 授权明确不提供所需视频/直播数据，另立“TikTok Business/创作者数据连接器”子项目。
4. 两类连接器必须保持独立授权、独立同步账本、独立原始数据和独立平台模型；只能通过带来源信息的内部读取模型汇合。

## 2. 稳定性准入门槛

只有测试店铺和至少一个生产店铺连续 14 天同时满足下列条件，才允许为后续能力编写技术方案或发起只读探针：

| 检查项       | 准入条件                                                             | 验证来源               |
| ------------ | -------------------------------------------------------------------- | ---------------------- |
| 最后成功同步 | 每个已开放店铺的 `video`、`live` 实体均不超过一个计划同步周期        | `GET /api/sync-health` |
| 数据缺口     | 每个店铺/实体 `dataGapCount = 0`                                     | `GET /api/sync-health` |
| 死信         | 每个店铺/实体 `deadLetterCount = 0`                                  | `GET /api/sync-health` |
| 失败率       | 近 7 天每个店铺/实体 `failureRate <= 5%`                             | `GET /api/sync-health` |
| 429          | 不存在因 429 导致的漏批或死信；所有限流均遵守 `Retry-After`          | 同步运行记录与安全日志 |
| 数据质量     | 无未处理的缺失日期、金额/币种冲突或源时间倒退告警                    | Analytics 质量告警     |
| 灰度回滚     | `test -> single -> all` 每阶段均完成验收，`placeholder` 回滚经过演练 | 发布记录               |

任何一项失败都会重新计算连续稳定天数。不得用平均值掩盖单个店铺或单个实体异常，也不得用 Mock 数据完成稳定性验收。

## 3. 稳定后才评估的能力

以下项目当前均为 `deferred`，不是已承诺功能：

1. **小时级实时数据**：先验证官方小时 endpoint 的实际刷新延迟、最近可查日期和限流，再决定轮询频率；直播结束后的分钟数据不能描述为在播实时数据。
2. **更多视频字段**：只有官方字段和真实响应同时确认后才能进入内部 DTO；未知或推测字段继续保留在后端原始载荷，不直接进入 UI。
3. **直播商品明细**：先验证大场次返回上限、分页行为和商品 ID 口径，再设计直播场次与商品明细关系。
4. **广告归因**：聚合报表不能写成单笔订单归因；只有同时包含订单键和广告证据的接口才能进入订单证据层，冲突仍按现有规则保留双方证据。
5. **导出功能**：只从 ERP 本地读取模型导出；必须具备权限、租户/店铺隔离、审计、行数上限、异步任务、过期下载和 PII 脱敏，不允许浏览器直接导出平台原始响应。

每项能力都必须依次经历 `documented -> probe_verified -> approved -> implemented -> staged`，不能因 Seller Center 页面可见就跳过官方能力与授权核验。

## 4. 另立连接器子项目的触发条件

满足任一条件时，停止向 TikTok Shop Analytics 模型追加兼容字段，并创建独立的 TikTok Business/创作者数据连接器子项目：

- 官方文档明确 TikTok Shop Seller API 不提供目标字段或目标账号范围。
- 当前应用类目、区域或 Seller scope 无法合法获取目标数据。
- 真实只读探针确认返回只覆盖官方/营销账号，无法满足已批准的创作者数据需求。
- 目标能力要求 TikTok for Business、Marketing API 或创作者本人授权。

浏览器监听、CSV/XLSX 导出和 Seller Center 私有请求只能用于受控验证或应急取证，不能被包装成 TikTok Shop 官方数据能力。

## 5. 连接器隔离规则

TikTok Business/创作者数据连接器必须满足以下硬边界：

- 使用独立 OAuth client、redirect URI、state 命名空间、scope 清单和 token 加密用途；不得复用 TikTok Shop Seller access token。
- 使用独立连接表、同步运行表、游标、死信、限流指标和原始载荷保留策略。
- 平台原始 ID 必须带连接器命名空间，不能仅凭相同字符串认定与 Shop 的店铺、达人、视频或直播为同一实体。
- 连接器原始数据不得直接写入 TikTok Shop Analytics 业务表，也不得复用 Shop endpoint 的解析 DTO。
- 只有经过显式身份映射、来源记录和冲突处理后，才能投影到 ERP 的统一只读分析模型。
- 两套授权必须能够独立撤销、刷新、暂停同步、回放死信和删除其持有的数据，不得互相影响。

建议子项目使用独立部署边界和数据库 schema；是否拆成独立仓库，在完成授权产品与数据保留要求核验后决定。

## 6. 当前允许的工作

稳定性门槛通过前，只允许：

- 修复当前日级同步、质量告警和展示问题；
- 完成测试店铺、单生产店铺和全部店铺灰度；
- 监控最后成功时间、延迟、失败率、429、死信和数据缺口；
- 维护能力矩阵与脱敏探针记录；
- 演练 `VITE_DATA_ROLLOUT_STAGE=placeholder` 回滚。

任何扩展必须在任务说明中引用本文件，并明确当前门槛是否已经通过。
